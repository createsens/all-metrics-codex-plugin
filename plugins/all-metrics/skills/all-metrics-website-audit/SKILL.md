# All Metrics Website Audit

Работать только через read-only инструменты MCP All Metrics. Ничего не менять на сайте и в подключениях.

## Проверить совместимость перед работой

1. Прочитать фактический список инструментов сессии. Обязательные: `get_current_user`, `list_sources`, `list_connections`, `list_resources`, `website`. Минимальная версия сервера All Metrics — 3.1.0.
2. Если `website` отсутствует, остановиться и сообщить, что сервер All Metrics не предоставляет инструмент `website` и требуется версия не ниже 3.1.0. Не подменять аудит собственным обходом сайта и не пересказывать содержимое страниц по памяти.
3. Полный контракт требований — [compatibility.json](../../compatibility.json), раздел `skills["all-metrics-website-audit"]`. Значение операций и статусов — [operations.md](references/operations.md).

## Различать сохранённый аудит, живой осмотр и новый обход

Это главное правило skill.

| Операция | `result_source` | Что это | Что нельзя говорить |
| --- | --- | --- | --- |
| `list_audits`, `latest_audit`, `get_audit`, `findings`, `pages`, `page`, `issues`, `checks`, `performance`, `robots`, `sitemaps`, `crawl_urls`, `visual`, `compare` | `saved` | Чтение уже сохранённого неизменяемого обхода по его UUID | Нельзя называть это свежим или только что выполненным аудитом |
| `inspect` | `live_inspect` | Одно наблюдение одной страницы прямо сейчас | Нельзя называть это аудитом сайта |
| `start_crawl` | `new_crawl` | Запуск нового обхода, создаёт новый UUID | Нельзя объявлять аудит выполненным до терминального статуса `crawl_status` |

Всегда указывать в ответе UUID обхода и его дату. Все разделы одного отчёта должны относиться к одному UUID, если пользователь явно не просит сравнение.

## Найти сайт

На сервере 3.4.0 исследование любого публичного URL не требует постоянного Website источника. По явной просьбе использовать `inspect_external_url` для страницы или `crawl_external_site` для сайта с URL и необязательным business_id, без resource_id. Результаты сохраняются в owner-scoped WebsiteTarget; старые resource_id операции совместимы. Serper используется отдельно для Google SERP, не для содержимого сайта.

1. При явном публичном URL сразу вызвать `inspect_external_url` или `crawl_external_site` с `url`. Не требовать добавления Website, Connection, resource_id или подтверждения владения. Отсутствие URL в каталоге не является отказом. При SERP-конкуренте передать `business_id` и `serp_snapshot_ids` исходной выдачи.
2. Только для выбора добавленного сайта или его истории вызвать `website` с `operation=list`. Эта операция возвращает все сайты пользователя даже после временной ошибки доступности.
2. Не выполнять принудительное обновление ресурсов, чтобы «проверить» наличие сайта: таймаут доступности не означает, что источник удалён.
3. Если сайтов несколько и выбор не следует из запроса, показать список и задать один уточняющий вопрос.
4. Добавление публичного сайта не требует OAuth и подтверждения владения; это не запускает обход.

## Получение содержимого и браузер

Сервер Website recovery принимает `render=auto|always|never` и `browser_provider=auto|browserless|local`. По умолчанию использовать auto. `browser_capabilities` показывает отдельные подтверждения ключа, Usage API, browser smoke и онлайн-статус агента. Наличие ключа не доказывает доступность браузера. При устаревшей схеме клиента обновить MCP tools/list/подключение; не объявлять, что внешний URL запрещён сервером, если клиент не публикует актуальный контракт.

`waiting_for_worker` означает сохранённое задание, ожидающее включённого локального агента; `needs_user_action` — ручную проверку в его браузере. Для inspect читать `browser_task_status` с task_id, для crawl — `crawl_status` с UUID. Не запускать повторный аудит для ожидания уже выданного задания. Открытый Hub не требуется; компьютер и агент должны работать. Не запрашивать ключи или cookies в чате.

При `content_status=challenge|unavailable` не делать выводы об отсутствии Title, H1, Description. Отмечать blocked_by_hosting/needs_user_action и inconclusive проверки. Сохранённый HTTP 403 и отдельный browser HTTP 200 — разные наблюдения. Защитные заглушки исключены из audited coverage; полный аудит не доказан только screenshot или HTML от /unblock. PSI 429, отсутствие ключа CrUX и отсутствие полевых данных описывать как ограничения performance-слоя.

Browserless работает в пределах доступных units и лимитов владельца. Не предлагать автоматические покупки или гарантированное прохождение любой защиты. При неизвестной/нулевой квоте сервер выбирает доступный локальный резерв либо сообщает причину ожидания.

## Прочитать сохранённый аудит

1. `operation=list_audits` — история обходов с датами и статусами.
2. `operation=latest_audit` — последний завершённый обход. Если пользователь не указал дату, использовать его.
3. `operation=get_audit` — сводка выбранного обхода: объём, статусы ответов, сводные показатели.
4. `operation=checks` — полный перечень выполненных проверок с результатом каждой. Это основа доказательной части.
5. `operation=findings` и `operation=issues` — найденные проблемы с уровнем серьёзности и затронутыми URL.
6. `operation=pages` и `operation=page` — постраничные данные: коды ответов, title, description, заголовки, канонические адреса, индексируемость, вес и время ответа.
7. `operation=robots` и `operation=sitemaps` — директивы robots.txt и карты сайта с ошибками разбора.
8. `operation=crawl_urls` — полный список обойдённых URL, включая исключённые и причину исключения.
9. `operation=performance` — PageSpeed Insights и поля CrUX. Лабораторные и полевые данные не смешивать: PSI — лабораторная симуляция, CrUX — реальные пользователи за 28 дней.
10. `operation=visual` — скриншоты; MCP-ресурсы дают HTML-снимки и изображения.
11. При наличии `analyze_audit_bundle` использовать его для структурированной сводки, а `get_audit_methodology` — чтобы корректно описать методику проверки.

Получать все страницы результатов постранично до конца. Не делать выводов по первой странице выдачи.

## Запустить новый обход только по явной просьбе

1. Убедиться, что пользователь просит именно новый обход, а не чтение сохранённого.
2. Вызвать `operation=start_crawl` и сохранить полученный UUID.
3. Опрашивать `operation=crawl_status` до терминального статуса. Не сообщать о завершении раньше.
4. При провале обхода назвать причину из ответа и не выдавать частичные данные за полный аудит.
5. Для проверки одной страницы использовать `operation=inspect` вместо полного обхода.

## Сравнить два обхода

Использовать `operation=compare` с двумя UUID. В сравнении показывать: что появилось, что исчезло, что изменило статус. Сопоставлять только обходы с сопоставимыми настройками и объёмом; при разном объёме обхода предупредить, что часть различий объясняется покрытием, а не изменениями сайта.

## Дополнить данными поиска

- Google Search Console — органические показы, клики, позиции и покрытие. Использовать только для SEO, не смешивать с PPC.
- Яндекс Вебмастер (`yandex_webmaster`) — только для подтверждённых сайтов: индексация, диагностика, внешние ссылки.
- Google Analytics 4 или Яндекс Метрика — поведение на проблемных страницах.

Если эти источники не подключены, раздел индексации строить только по доказательствам обхода и явно пометить его как неполный.

## Подготовить ответ

По умолчанию дать:

1. Шапку: домен, UUID обхода, дата обхода, число обойдённых URL, `result_source`.
2. Краткий вывод: техническое состояние и три проблемы с наибольшим влиянием.
3. Таблицу проблем: серьёзность, проблема, число затронутых URL, примеры URL, чем подтверждено, что делать.
4. Блок индексации: robots.txt, sitemap, канонические адреса, noindex, коды ответов, дубли.
5. Блок контента: title, description, H1, дубли и пустые значения.
6. Блок ссылок: битые внутренние ссылки, цепочки редиректов, глубина вложенности.
7. Блок скорости: PSI отдельно, CrUX отдельно, с указанием устройства и даты сбора.
8. План работ по приоритету с оценкой трудоёмкости и ожидаемым эффектом.
9. Ограничения: какие проверки не выполнялись, какие страницы исключены из обхода и почему.

Каждое утверждение опирать на конкретную проверку или URL из обхода. Не использовать общие SEO-рекомендации вместо находок. Отсутствие данных обозначать явно, а не трактовать как отсутствие проблемы.
