# All Metrics Cross-Source Report

Работать только через read-only инструменты MCP All Metrics. Не выводить персональные данные и токены.

## Проверить совместимость перед работой

1. Прочитать фактический список инструментов сессии. Обязательные: `get_current_user`, `list_sources`, `list_connections`, `list_resources`, `list_fields`, `preview_data`, `start_query`, `get_query_status`, `get_query_results`. Минимальная версия сервера All Metrics — 3.2.0.
2. При отсутствии обязательного инструмента остановиться и назвать его точное имя и требуемую версию сервера.
3. Полный контракт требований — [compatibility.json](../../compatibility.json), раздел `skills["all-metrics-cross-source-report"]`. Правила расчёта — [attribution.md](references/attribution.md).

## Построить карту покрытия до сбора данных

1. Вызвать `list_sources`, `list_connections` и `list_resources` с `selected_only=true` и `queryable_only=true`.
2. Составить таблицу покрытия: источник, статус подключения, выбранный ресурс, попадает ли в отчёт.
3. Присвоить каждому источнику один статус: `ready`, `not_connected`, `no_resource`, `auth_required`, `error`.
4. Эту таблицу включить в итоговый ответ до самих цифр. Читатель обязан видеть границы отчёта раньше выводов.
5. Ни один раздел отчёта не строится по источнику со статусом отличным от `ready`. Раздел помечается как недоступный с указанием причины.

Соответствие источников разделам отчёта:

| Раздел | Источники |
| --- | --- |
| Платный трафик | `google_ads`, `yandex_direct` |
| Поведение на сайте | `google_analytics`, `yandex_metrica` |
| Органический поиск | `google_search_console`, `yandex_webmaster` |
| Локальный поиск | `google_business_profile` |
| Звонки | `callrail` |
| Заявки, сделки, выручка | `bitrix24` |
| Техническое состояние сайта | `website` |
| Спрос и семантика | `google_keyword_planner`, `yandex_wordstat` |

## Зафиксировать период и сопоставимость

- Если период не указан, использовать текущий календарный месяц с 1-го числа по сегодня и сравнивать с тем же числом дней предыдущего месяца.
- Один период для всех источников. Если источник отдаёт данные только за другой интервал, показать этот интервал отдельной строкой и не сравнивать его напрямую с остальными.
- Указать часовой пояс каждого источника, если они различаются. Различие часовых поясов — известная причина расхождений на границах периода.
- Отдельно предупредить о задержках: CRM-сделки, импорт офлайн-конверсий и полевые данные приходят позже рекламных.

## Собрать данные

1. Для каждого `ready`-источника вызвать `list_fields` и использовать фактически доступные поля. Не предполагать схему.
2. При необходимости проверить значения измерений через `preview_data`.
3. Выполнять выборки через `start_query` → `get_query_status` → `get_query_results` и забирать все страницы.
4. Для Website использовать инструмент `website` — общие инструменты выборки его не поддерживают.
5. Для Google Business Profile использовать инструмент `google_business_profile`: сначала `locations`, затем нужные операции. Локальные показы GBP — не позиции и не показы рекламы.
6. Для CallRail использовать инструмент `callrail`. Аудиозаписи и ссылки на плеер не возвращаются и не запрашиваются.
7. Для Bitrix24 соблюдать ограничения воронки из [attribution.md](references/attribution.md).
8. `get_export_link` вызывать только по явной просьбе о выгрузке.

## Собрать воронку

Строить единую воронку и на каждом шаге указывать источник данных:

1. Показы и охват — рекламные системы, GBP, Search Console.
2. Клики и визиты — рекламные системы против веб-аналитики. Расхождение 5-15% между кликами и сеансами нормально; расхождение выше нужно объяснить.
3. Целевые действия на сайте — GA4 и Метрика.
4. Звонки — CallRail.
5. Заявки — Bitrix24, уникальные сделки нужной воронки.
6. Продажи и выручка — сделки `WON` и `OPPORTUNITY` с валютой.

Каждый переход воронки сопровождать коэффициентом конверсии и полнотой атрибуции.

## Рассчитать показатели

- `CTR = клики / показы × 100%`
- `CPC = расходы / клики`
- `CPA рекламы = расходы / конверсии рекламной системы`
- `CPL = расходы / атрибутированные уникальные сделки`
- `CPS = расходы / атрибутированные сделки WON`
- `Конверсия клик → заявка = атрибутированные сделки / клики × 100%`
- `Конверсия заявка → продажа = атрибутированные WON / атрибутированные сделки × 100%`
- `ROAS = атрибутированная выручка WON / расходы × 100%`
- `ROI (ROMI) = (атрибутированная выручка WON − расходы) / расходы × 100%`
- `Доля канала в расходах` и `доля канала в выручке` — для сравнения каналов между собой.

При нулевом знаменателе выводить `н/д`, а не ноль. Не смешивать CPA рекламной системы и CPL CRM. Не суммировать разные валюты; конвертировать только при явном курсе и дате курса. При отсутствии надёжной атрибуции не рассчитывать CPL, CPS, ROAS и ROI по отдельному каналу — рассчитывать только сводно и помечать это.

## Подготовить ответ

По умолчанию дать:

1. Таблицу покрытия источников со статусами.
2. Краткий вывод: бизнес-результат периода и главное изменение.
3. Сводную таблицу за период и сопоставимый прошлый период с абсолютным и процентным изменением.
4. Таблицу по каналам: расходы, клики, заявки, CPL, продажи, выручка, ROAS, ROI, доля в расходах и в выручке.
5. Воронку с коэффициентами переходов и полнотой атрибуции.
6. Отдельный блок органики и локального поиска, не смешанный с платным трафиком.
7. Блок технического состояния сайта, если источник `website` доступен, со ссылкой на UUID обхода.
8. Расхождения между источниками с объяснением причины каждого.
9. Выводы и приоритетные действия с ожидаемым эффектом.
10. Ограничения: неполная атрибуция, задержки, разные часовые пояса, недоступные источники.

Отделять факты от выводов и не выдавать корреляцию за причинность. Для аудита настроек рекламы передавать работу в `all-metrics-ppc-audit`, для технического аудита сайта — в `all-metrics-website-audit`, для новой семантики — в `all-metrics-keyword-planner`.
