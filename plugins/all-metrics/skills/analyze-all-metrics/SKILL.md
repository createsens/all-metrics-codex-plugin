# Analyze All Metrics

Работать только через read-only инструменты MCP All Metrics. Не изменять подключения, кампании или CRM и не выводить токены.

## Проверить совместимость перед работой

1. Прочитать фактический список инструментов текущей сессии. Не считать инструмент доступным по названию skill, документации или прошлой сессии.
2. Обязательные инструменты: `get_current_user`, `list_sources`, `list_connections`, `list_resources`, `list_fields`, `preview_data`, `start_query`, `get_query_status`, `get_query_results`. Минимальная версия сервера All Metrics — 3.0.0.
3. При отсутствии обязательного инструмента остановиться, назвать его точное имя и требуемую версию сервера и предложить обновить All Metrics. Не подменять его другим сервисом.
4. Полный контракт требований — [compatibility.json](../../compatibility.json), раздел `skills["analyze-all-metrics"]`.
5. Если подключение не работает или источник не виден, сначала выполнить `all-metrics-diagnostics` и только потом продолжать анализ.

## Разделить фактический анализ и планирование

- Для фактической статистики действующих кампаний продолжить работу этим skill.
- Для аудита настроек рекламного кабинета и поиска ошибок конфигурации использовать `all-metrics-ppc-audit`.
- Для технического SEO-аудита сайта использовать `all-metrics-website-audit`.
- Для сквозного отчёта с CRM-экономикой по всем источникам использовать `all-metrics-cross-source-report`.
- Для Яндекс Wordstat, его частотности, похожих запросов, регионального спроса и семантического ядра использовать `all-metrics-wordstat`. Не подменять его Google Keyword Planner.
- Для Google Keyword Planner, рекламной конкуренции, ставок и прогнозов использовать отдельный skill `all-metrics-keyword-planner`.
- Если запрос объединяет аудит кампании и поиск новых ключей, сначала получить фактические показатели этим skill, затем применить `all-metrics-keyword-planner`.
- Не смешивать фактические метрики Google Ads и Яндекс Директа с прогнозами Keyword Planner. Подписать прогноз отдельным блоком.

## Найти объект анализа

Если доступны `list_businesses`, `list_business_resources` и `get_business_context`, сначала использовать подтверждённый Business context и конкретные связи ресурсов. Для брифа, Serper SERP и конкурентов использовать `all-metrics-business-research`; не смешивать выдачу с Website crawl или частотностью.

1. Вызвать `list_sources`, `list_connections` и `list_resources`.
2. Найти сервис, бренд, домен, аккаунт или кампанию без учёта регистра по полному и частичному совпадению названия. Учитывать варианты написания и домены.
3. Искать рекламу одновременно в Google Ads и Яндекс Директе, если пользователь не ограничил платформу.
4. Подключить GA4 и Яндекс Метрику для анализа поведения и конверсий найденного сайта. Использовать Google Search Console только для SEO, органического поиска и поисковых запросов; не смешивать его данные с PPC.
5. Для локального бизнеса использовать `google_business_profile`: сначала `locations`, затем нужные операции `profile`, `status`, `performance`, `search_keywords`, `reviews`, `changes` или `audit`. GBP search keywords являются помесячными локальными показами, а не позициями и не PPC impressions.
6. Если совпадение однозначно, продолжить без вопроса. Если вариантов несколько или связь сервиса с ресурсом неочевидна, сначала собрать доступные варианты, затем показать их пользователю и задать один точный уточняющий вопрос. Не спрашивать то, что можно определить инструментами.

## Определить период

- Если период не указан, использовать текущий календарный месяц с 1-го числа по сегодня.
- Сравнивать с тем же количеством дней предыдущего месяца: например, 1-23 июля с 1-23 июня.
- Использовать часовой пояс рекламного аккаунта или аналитического ресурса; при его отсутствии - часовой пояс пользователя. Указать часовой пояс, если он влияет на границы периода.
- Для неполного текущего дня предупредить, что данные за сегодня могут дозагружаться.

## Получить данные

1. Перед запросом вызвать `list_fields` для каждого нужного источника и использовать фактически доступные поля, а не предполагать схему.
2. При необходимости применить `preview_data`, чтобы проверить значения измерений, названия кампаний, события, этапы и поля атрибуции.
3. Запустить выборку через `start_query`, проверить её через `get_query_status`, затем получить все необходимые страницы через `get_query_results`.
4. Использовать `list_saved_queries` и `run_saved_query`, только если подходящий сохранённый запрос уже решает задачу. Запрашивать `get_export_link` только когда пользователь просит выгрузку.
5. При ошибке запроса сверить поля через `list_fields`, исправить запрос и повторить один раз. Если обязательных данных нет, явно указать пробел, источник и влияние на вывод.

Для рекламы собирать минимум:

- показы;
- клики;
- расходы и валюту;
- CTR;
- CPC;
- конверсии и события;
- CPA рекламной системы.

По необходимости добавлять кампании, группы, объявления, поисковые запросы, устройства, регионы, сети и динамику по дням. Не суммировать разные валюты. Конвертацию выполнять только при наличии явного курса и даты курса.

## Ограничить Bitrix24

- Анализировать только сделки воронки «Онлайн заявки» с `CATEGORY_ID = 6`.
- Полностью игнорировать сделки других воронок.
- Считать заявку как уникальную сделку по ID, созданную в анализируемом периоде.
- Получать только контакты, связанные с отобранными сделками. Использовать их для проверки связи и дедупликации, но не считать контакты заявками и не выводить персональные данные.
- Считать продажой сделку со статусом `WON`, закрытую в анализируемом периоде.
- Брать выручку из `OPPORTUNITY` и учитывать валюту сделки.
- Связывать сделку с рекламой только по фактическим данным атрибуции: UTM, `gclid`, `yclid` или другому доступному идентификатору. Не распределять неатрибутированные сделки предположительно.
- Если атрибуция неполная, отдельно показать атрибутированные, неатрибутированные и общие сделки, а также долю полноты атрибуции.

## Рассчитать показатели

Пересчитывать производные показатели из полученных исходных значений и сверять их с показателями источника:

- `CTR = клики / показы × 100%`
- `CPC = расходы / клики`
- `CPA рекламы = расходы / конверсии рекламной системы`
- `CPL CRM = расходы / атрибутированные уникальные сделки`
- `CPS = расходы / атрибутированные сделки WON`
- `Конверсия клик → заявка = атрибутированные сделки / клики × 100%`
- `Конверсия заявка → продажа = атрибутированные WON / атрибутированные сделки × 100%`
- `ROAS = атрибутированная выручка WON / расходы × 100%`
- `ROI рекламы (ROMI) = (атрибутированная выручка WON - расходы) / расходы × 100%`

При нулевом знаменателе выводить `н/д`, а не ноль. Не смешивать CPA рекламной системы и CPL CRM. Не считать источник-специфичные CPL, CPS, ROAS или ROI без надёжной атрибуции. Если расходы и выручка в разных валютах, сначала запросить правило конвертации или показать, что показатель рассчитать нельзя.

## Подготовить ответ

По умолчанию дать:

1. Краткий вывод с главными изменениями и бизнес-результатом.
2. Полную сравнительную таблицу: текущий период, прошлый сопоставимый период, абсолютное и процентное изменение.
3. Разбивку по платформам и найденным кампаниям.
4. Отдельный блок CRM: заявки, CPL, WON, CPS, выручка, ROAS, ROI/ROMI и полнота атрибуции.
5. Найденные проблемы только с опорой на данные.
6. Приоритетные рекомендации по корректировкам и ожидаемому эффекту.
7. Краткие оговорки о неполных, задержанных или несопоставимых данных.

Отделять факты от выводов. Не выдавать корреляцию за причинность. Если пользователь задал узкий вопрос, сначала ответить на него, затем добавить только необходимые показатели и контекст.
